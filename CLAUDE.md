# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Run everything from the repo root. `make help` lists the top-level targets.

```bash
make docker-up          # postgres + redis + kafka + elasticsearch
make migrate            # shared migrations only (needs DATABASE_URL)
./dev.sh                # all 6 services locally (sources .env, runs make migrate first)
make build-auth         # build one service binary -> bin/auth
make gen                # sqlc generate (auth only; requires sqlc on PATH)
make tidy               # go work sync + go mod tidy across every module
make gen-keys           # RS256 keypair into keys/ for JWT signing
```

Tests — this is a Go **workspace**, so `go test ./...` from the root only covers the current module. Use per-module invocations:

```bash
make test                                         # root module only
(cd shared/pkg && go test ./...)                  # where the tests actually live
(cd services/orders && go test ./...)
(cd shared/pkg && go test -run TestEncrypt ./crypto)   # single test
(cd shared/pkg && go test -v -count=1 ./money)         # no cache
```

Test coverage is currently limited to `shared/pkg` (crypto, money, errors).

## Architecture

Go 1.25 workspace: one module per service under `services/`, plus `shared/pkg` and `scripts/migrate`. Module path prefix is `github.com/activialtd/gomarketi.com-backend/`. Adding a module means adding it to `go.work`, the `SERVICES` list in the `Makefile`, `scripts/gen/gen.sh`, and the path filters in `.github/workflows/deploy.yml`.

### Request flow and the auth boundary

`services/gateway` is a plain Go reverse proxy (`net/http/httputil`, no Gin) and is **the only component that validates JWTs**. It parses the RS256 Bearer token with `JWT_PUBLIC_KEY`, then injects `X-User-ID` and `X-Store-IDs` headers before proxying. Downstream services never see the token — they read those headers through `shared/pkg/middleware.UserContext()`. The doc comments in `shared/pkg/middleware` still say Envoy injects these headers; that is stale, the Go gateway does it now. Because downstream services trust the headers unconditionally, they must never be exposed publicly.

Gateway specifics in `services/gateway/cmd/server/main.go`:
- Upstreams come from env: `UPSTREAM_AUTH` and `UPSTREAM_STOREFRONT` are required; `UPSTREAM_IDENTITY`, `UPSTREAM_CATALOGUE`, `UPSTREAM_ORDERS` are optional and their routes are skipped when unset. `/v1/crm/`, `/v1/analytics/`, and `/v1/wallet/` all route to `UPSTREAM_ORDERS`.
- Unauthenticated prefixes: `/v1/auth/`, `/v1/storefront/public/`, `/v1/catalogue/public/`, `/v1/orders/public`.
- `needsStoreIDs()` decides which prefixes get `X-Store-IDs`; when the JWT lacks `store_ids` the gateway looks the store up from storefront and caches it (5 min, 5 s for misses). A new store-scoped prefix must be added to the upstream map **and** to `needsStoreIDs`.
- SSE/WebSocket clients cannot set headers, so a `?token=` query param is promoted to `Authorization`.

### Migrations — two independent systems, one database

All services share a single `DATABASE_URL`.

1. `shared/migrations/*.sql` — auth and identity tables (users, auth identities, OTP, refresh tokens, profiles, plans). Applied only by `go run ./scripts/migrate` (`make migrate`, also run by `dev.sh`), tracked in `schema_migrations`.
2. `services/{catalogue,orders,storefront}/db/migrations/*.sql` — embedded with `go:embed` and applied **automatically at service startup** by that service's `db.Migrate`, tracked in a separate `_migrations` table.

`shared/migrations/0006` requires **PostGIS** (`CREATE EXTENSION postgis`, a `GEOMETRY(POINT, 4326)` column with a GIST index) — the only extension any migration needs. The plain `postgres` image cannot run it, so docker-compose uses a PostGIS build; on Apple Silicon that image is amd64-only and runs emulated.

So a new orders table needs no migrate run — just restart the service. A new shared table needs `make migrate`, and if it belongs to auth it must also be added to the `schema` list in `services/auth/sqlc.yaml`.

### Service internals

Each service follows `cmd/server/main.go` (wiring, config, shutdown) → `internal/handler` (Gin; `routes.go` registers) → `internal/service` (business logic) → SQL. Config is viper: `.env` file plus `AutomaticEnv`, so real env vars win.

Two different data-access styles, despite identical directory names:
- **auth** — `internal/repository/queries/*.sql` compiled by sqlc into `internal/repository/db` (`// Code generated by sqlc. DO NOT EDIT.` — change the `.sql` and run `make gen`). It is the only service with a `sqlc.yaml`.
- **identity** — `internal/repository/db` is *hand-written* despite the same layout; edit it directly.
- **catalogue, orders, storefront** — no repository layer at all; raw `sqlx` queries inline in `internal/service`.

Errors: return `shared/pkg/errors` constructors (`NotFound`, `BadRequest`, `Conflict`, `TooManyRequests`, …); they carry the HTTP status via `HTTPStatus()` and handlers map them to responses. Use `fmt.Errorf("...: %w", err)` for anything internal.

### Markets and delivery options

`markets` is an admin-curated reference table (seeded in storefront migration 0008); `stores.market_id` is a nullable FK into it, and every store payload carries `market_id` + `market_name`. `store_delivery_options` holds each vendor's own delivery choices (title, description, price_kobo) — they replace the hardcoded `DELIVERY_ZONES` list in the web checkout.

The fee is authoritative server-side: `resolveDeliveryFee` in orders reads the price straight from `store_delivery_options` by `delivery_option_id`, so a client cannot invent one. A bare `delivery_fee_kobo` is honoured only for stores with no options configured. `orders.total_kobo` is items **plus** delivery, and Paystack is verified against that sum with an exact match, so any change to how the total is computed must change both sides together.

### Search

`GET /v1/catalogue/public/search` is the unified search: products and vendors for one query, plus `related_products` (shared category/tag) and `suggestions` (completions from names and tags). `type=products|vendors` narrows it; `/v1/catalogue/public/products/search` is the same engine in the paginated shape the consumer app expects.

Matching is trigram (`pg_trgm`) plus a generated `search_doc` tsvector on products, so misspellings and partial words hit. Two details to preserve when editing `services/catalogue/internal/service/search.go`: only the `%` operator can use the GIN trigram index — `similarity() >= x` cannot, so both clauses are present, `%` for speed and `similarity()` for a threshold that holds even on connections that predate the database setting in migration 0004. And a bare integer in `ORDER BY` is a column ordinal, which is why the empty-query rank is `0::float`.

### Money: escrow and the delivery fee

The fulfilment lifecycle is `pending → confirmed → at_hub → shipped → delivered` (or `cancelled`). `at_hub` means the vendor handed the parcel to GoMarketi, not that the buyer has it, so it deliberately does not release escrow; `shipped` sets `dispatched_at`, which starts the auto-release clock.

Buyer-facing reads (`GET /v1/orders/mine`, `/mine/:id`) match on the signed-in user's **email**, not a user id: checkout is public and `customer_id` is derived from store+email, so email is the only identity that spans stores. A buyer whose account has no email gets a clear error rather than an empty list.

A sale credit is written to `wallet_transactions` as `pending`, not `completed`, and `GetWallet` sums only completed rows — so a vendor cannot withdraw before the buyer has the goods. `orders.escrow_status` tracks that money: `held` → `released` (buyer confirms via `POST /v1/orders/public/:id/confirm-delivery`, or the hourly sweep in `escrow.go` auto-releases `AutoReleaseAfter` past `dispatched_at`) → or `reversed` when the order is cancelled, which marks the credit `failed`. The order row and the ledger row are always flipped in one transaction; keep it that way.

The delivery fee is never credited to a vendor — the platform delivers, so it keeps it. For a multi-vendor checkout the fee lives on the `checkouts` row and is charged once for the basket; each order carries only its own items, so summing orders never double-counts it.

### Real-time (orders)

`services/orders/internal/sse` fans out order and wallet events. With `REDIS_URL` set it uses Redis pub/sub with event replay so multiple instances stay consistent; without it (or if Redis is unreachable) it silently falls back to an in-memory broker that only works single-instance.

### Email

Auth picks a provider by which key is set, in order: Brevo → Resend → Mailgun → SMTP. Orders and storefront have their own `internal/email` packages for order/invoice mail. Railway blocks outbound SMTP, so Brevo's HTTP API is the production path.

## Local ports

`dev.sh` overrides `PORT` per service, and the in-code defaults do **not** match it — always trust `dev.sh`: gateway 8080, auth 8086, identity 8082, storefront 8083, catalogue 8084, orders 8085. Auth deliberately avoids 8081: that is Metro/Expo's default, and the consumer app cannot start its bundler if a service holds it. Only the gateway should be hit from a frontend.

## Deployment

Railway, one service per Railway app (`services/*/railway.toml`, `deploy-railway.sh`, `.env.railway.template`). `.github/workflows/deploy.yml` deploys only the services whose paths changed — note that any `shared/pkg/**` change redeploys all five Go services. In production, JWT keys are supplied as base64 PEM (`JWT_PRIVATE_KEY_B64` / `JWT_PUBLIC_KEY_B64`) rather than the `*_PATH` files used locally.

`.env.example` has drifted from the code — several live vars (`BREVO_*`, `PAYSTACK_SECRET_KEY`, `SUPABASE_PUBLIC_URL`, `SMILE_ID_*`, `STOREFRONT_ROOT_DOMAIN`, `VENDOR_BASE_URL`, `UPSTREAM_*`) appear only in `.env.railway.template` or in the code. Grep for `viper.GetString(` / `os.Getenv(` when hunting for a config name.
